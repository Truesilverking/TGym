# TGym: auditoría de plataforma y datos, 2026-10-19

Esta matriz complementa la auditoría de rutinas/sesiones y los reportes. La fuente revisada es el checkout de TGym de esta sesión, empezando por `docs/ARCHITECTURE.md`. Las pruebas usan exclusivamente perfiles sintéticos, stores de happy-dom/mocks o una API local con directorio temporal propio. No se abrieron perfiles privados, no se conectó Google Drive real ni se enviaron notificaciones o archivos a terceros.

## Nivel de evidencia

- **U**: prueba unitaria con entradas y salidas verificadas.
- **C**: interacción React/happy-dom, con inspección de estado y almacenamiento; no equivale a navegador o teléfono.
- **HTTP**: proceso API real, solicitudes HTTP locales y disco temporal, incluido reinicio del proceso.
- **S**: inspección de fuente; implementación inventariada, aceptación pendiente cuando se indica.
- **Pendiente**: integración/dispositivo no disponible o fuera de las pruebas ejecutadas; no se presenta como fallo.

## Defectos reproducidos y corregidos

### P1: un estado API de tipo array reemplazaba el perfil guardado

`PUT /api/data` comprobaba `typeof body.state === 'object'`; JavaScript incluye arrays en esa condición. El ensayo con un perfil sintético ya guardado devolvió **HTTP 200** a `{state: []}` y escribió el array en su archivo. La causa es la comprobación incompleta del tipo antes de `atomicWrite`.

La corrección añade `Array.isArray(body.state)` al rechazo existente, sin modificar el formato válido ni las reglas de sincronización. La regresión solicita `null`, `[]`, texto y un número; exige HTTP 400 y vuelve a leer el perfil después de cada solicitud para demostrar que conserva el anterior. El conjunto HTTP también conserva historia/peso/rutinas tras reiniciar el servidor y confirma que `active` sigue siendo local al dispositivo.

### P1: falta de espacio al deshacer una importación eliminaba la única copia Undo

Settings ejecutaba `consumeImportUndo()` antes de `replaceState()`. Esa lectura eliminaba la copia en sessionStorage; después, una excepción en la escritura primaria dejaba el perfil importado vigente y ya no permitía repetir Undo. La causa es consumir la recuperación antes de confirmar la escritura síncrona del perfil.

`restoreImportUndo` ahora conserva la copia hasta que `replaceState` termina correctamente. Settings presenta el error de almacenamiento sin afirmar éxito. La regresión usa una excepción `QuotaExceededError` en el `localStorage.setItem('gym_state_v1', ...)` real del store, comprueba que ambas copias anteriores siguen intactas y luego reintenta: recupera el perfil previo, lo lee desde localStorage y consume Undo una sola vez. Cancelar no cambia ninguna de las dos copias.

## Inventario de fuente adicional y límites

`Settings.jsx` también expone selección de equipo/perfiles, restricciones de repeticiones, varios descansos, pantalla encendida, feedback de sonido/vibración, preferencias de deload, idiomas EN/ES, backup/restore, conexión API/pareado y cierre de sesión. Los escenarios de entrenamiento y catálogo se cubren en la matriz del otro subsistema. `Login.jsx`, `MobileOnboarding.jsx` y `Admin.jsx` implementan las vistas sobre las rutas/API arriba inventariadas; pasar los handlers HTTP no certifica passkeys del SO ni cada interacción visual de esas vistas.

Pendientes concretos: iPhone real Safari/PWA y compilación Xcode; instalación/force-stop/biometría/cámara de Android real; recepción y toque de notificación con permisos del SO; Google Drive OAuth real y restauración desde otra cuenta/dispositivo; share sheets nativos y aceptación por aplicaciones receptoras; Health Connect con proveedor real; presión de almacenamiento/evicción real del SO; screen reader real y auditoría WCAG completa. Las mediciones automatizadas de viewport y los tiempos de suite no constituyen un benchmark de rendimiento móvil.
